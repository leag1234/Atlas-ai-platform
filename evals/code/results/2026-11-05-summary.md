# Code benchmark, phase 0: results of 2026-11-05

Twenty synthetic tasks (`evals/code/tasks/`), hidden checks run offline in `atlas-code-bench:local`
(`--network none`). Reference solutions pass 20/20 and an agent that changes nothing passes 0/20.
One attempt per task and configuration unless stated. Configuration A (reference models) was not run.

| Configuration | Harness | Model behind it |
|---|---|---|
| `codex-atlas` (B) | Codex CLI 0.153.4 in the benchmark container | Atlas API `atlas-code`, effort none (first route GLM 5.3 Flash) |
| `codex-atlas-high` (B) | same | Atlas API `atlas-code`, effort high (first route GLM 5.3) |
| `atlas-work` (C) | Atlas project Work mode, guest instance | `atlas-qwen` (Qwen 3.5 397B), one Work turn per task |

Cost: B is computed from Codex token counts and the provider prices of the first route (the worker key is
shared with other agents, so its usage delta is only an upper bound); C is the Work session's known cost.

## Reading the results

- **Model gap (B).** In a mature harness, Atlas models solve 15/20 (effort none) and 19/20 (effort high).
  Effort high costs about seven times more (0.82 against 0.11 EUR for the 20 tasks) at the same median time.
  Task 07 with effort none failed its first attempt (runaway loop, 181 steps, killed at 600 s); a rerun after
  a runner fix passed in 63 s (kept as `rerun` in the record, not counted). Single runs: expect a few points of
  variance.
- **Harness gap (C).** Work mode solves 5/20. Seven of its twenty turns ended on an infrastructure error
  before or during work (`provider_error` 422 three times, `dependency_unavailable` 503 four times, all with
  provider outcome `not_called`). On the 13 tasks without such an error: C 4/13, B effort none 11/13,
  B effort high 13/13. C and B do not use the same model, so this mixes model and harness; the gap is too large
  to be explained by the model alone (Qwen 3.5 397B against GLM 5.3 Flash).
- **False claims.** B effort none: 4 (tasks 14, 16, 17, 19), B effort high: 1 (task 16), C: 0. C has the
  opposite defect: its final reply says "The work did not complete: the step limit was reached." even when the
  hidden check passes (tasks 03 and 10), and task 06 ended without any reply.

## Main failure patterns

C (Work mode):
1. `loop_detected` ended 11 of 20 turns: the loop stops after three identical consecutive tool calls, typically
   an `edit_file` retried verbatim after `old_text_must_exist_exactly_once`. Codex keeps going after a failed
   tool call and changes approach.
2. Short endurance: wall limit 300 s, 40 tool calls, 0.20 EUR per session; with 10 to 50 s per model call a
   turn gets 4 to 12 model calls (median 4 tool calls here, against 7 to 9 steps for Codex).
3. No edit at all in 7 of the 13 turns without infrastructure error (05, 07, 08, 09, 13, 15, 20): the turn
   used only non-editing tools (reads, searches, plan, tool group switch), then stopped on `loop_detected`.
4. Infrastructure errors (7/20, see above). At the end of the run the test subject `claude-probe` hit its
   monthly limit ("Monthly limit reached: 30.43 EUR used of 30.00 EUR", HTTP 429), so a retry of the seven
   infrastructure failures was refused. The earlier 503/422 `not_called` errors may be budget reservation
   refusals reported as dependency errors (requirement D5); not verified.
5. An aborted first C run with `atlas-glm` (13 tasks, 0 passed) is not counted: 5 turns answered in prose with
   no tool call at all, 4 ended on 422 `invalid_request` and 3 on 503, both `not_called`.

B (Codex on Atlas):
1. Specification details missed, then success claimed: zero-activity days omitted (17), `extra` argument still
   mutated against the docstring (14), staging directory left behind by a rejected archive so the next install
   fails (19), duplicate total line (16, effort none) and the duplicate-order rule (16, effort high).
2. Runaway loop on 07 (effort none, first attempt) and one session cut by the Atlas API loop guard (02: HTTP 409
   after the same tool call 12 times; the work was already done and passed).

## Limits of this measurement

- The tasks are small (median 7 to 9 Codex steps); they discriminate harnesses well but are easier than work on
  a real repository. Harder tasks on pinned public repositories should be added before the exit criterion
  (90 percent of A) is used.
- C rebuilds the workspace from the per-edit diffs in the Work event stream because the guest Work session has
  no export route; all diffs applied in this run (0 failures), but a diff above 16,000 characters would be
  truncated by the event.
